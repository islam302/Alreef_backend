# Arabic, RTL and formatting

The storefront's default language is Arabic (`LANGUAGE_CODE = "ar"`), it sells in EGP,
and it runs on Africa/Cairo time. This is what the API gives you for each of those, and
where you have to fill gaps yourself.

## Which fields are bilingual

The API does **not** pick a language for you. Where content exists in both languages it
ships both, and the client chooses.

**Both `_en` and `_ar`:**

| Model | Fields |
|---|---|
| Product | `name_en`, `name_ar` |
| Category | `name_en`, `name_ar` |
| Attribute | `name_en`, `name_ar` |
| AttributeValue | `value_en`, `value_ar` |
| Governorate | `name_en`, `name_ar` |
| City | `name_en`, `name_ar` |

```ts
export const localized = <T extends Record<string, unknown>>(
  obj: T, base: string, lang: "ar" | "en"
): string => (obj[`${base}_${lang}`] as string) || (obj[`${base}_en`] as string) || "";

localized(product, "name", "ar"); // name_ar, falling back to name_en
```

Always fall back. `name_ar` is a non-null `CharField` but nothing stops an admin saving
an empty string, and an empty product name renders as a blank card.

**English-only — no Arabic column exists:**

| Field | Where |
|---|---|
| `description`, `short_description` | Product |
| `seo_title`, `seo_description` | Product, Category |
| `description` | Category |
| `name`, `description` | Brand |
| `name`, `description` | ShippingMethod |
| `alt_text` | ProductImage |
| `product_name_snapshot`, `variant_name_snapshot` | OrderItem |
| `product_name` | CartItem |
| `breadcrumbs[].name_en` | CategoryDetail |
| `shipping_address_snapshot.governorate` / `.city` | Order |

This matters more than it looks. An Arabic storefront will show Arabic product names on
the listing and detail pages — then switch to English the moment the user opens their
cart or an order, because `CartItem.product_name` and `OrderItem.product_name_snapshot`
are both populated from `name_en`. Same for breadcrumbs, and for the governorate name
frozen into an order's address snapshot.

Workarounds, worst to best:

1. Live with the mixed language. Fine for a soft launch, obviously not for production.
2. For the **cart**, ignore `product_name` and read through the nested variant:
   `item.variant` is a full `ProductVariant`, but it has no product object on it, so you
   still need the product name from somewhere — keep a `variant_id → product` map
   populated from the listing/detail queries you've already made, and fall back to
   `product_name`.
3. For **orders**, the snapshot is deliberate: it freezes what was bought, so it
   *shouldn't* be re-resolved live. `OrderItem.product` holds the product id when the
   product still exists, so you can fetch the current Arabic name for display while
   keeping the snapshot as the record. Decide which one is legally the receipt.
4. Ask the backend for `_ar` snapshot columns and an `name_ar` in breadcrumbs. This is
   the only real fix, and it's a small change on their side.

Flag it early rather than discovering it in QA.

## Server messages are English, always

There is no compiled `locale/` directory in the repo. `LOCALE_PATHS` points at a path
that doesn't exist, so `django.middleware.locale.LocaleMiddleware` has nothing to load
and sending `Accept-Language: ar` changes nothing.

Every `message` in the envelope — `"Invalid email or password."`, `"Coupon applied."`,
`"Order cancelled."` — comes back in English regardless.

So: **translate on the client, keyed on `errors.code`.** There's a bilingual message map
ready to copy in
[`ERROR-HANDLING.md`](./ERROR-HANDLING.md#a-message-map-you-can-copy). Use the envelope's
`message` only as a last-resort fallback for a code you haven't mapped, and don't design
a UI that shows raw server messages prominently.

The same applies to enum values: `status: "out_for_delivery"` is a machine value, and
there is no translated label for it anywhere in the API. Keep a label map — there's a
starter table in [`STATES.md`](./STATES.md#suggested-labels).

`profile.language` (`ar` | `en`) on the user record is stored but not acted on by the
backend. Treat it as the user's saved preference for *your* UI, and sync it with your
own language switcher.

## Money

Every amount is a **decimal string**: `"542.48"`, not `542.48`. That's `django-money`
plus DRF's `COERCE_DECIMAL_TO_STRING`, and it's deliberate — floats lose cents.

**Currency is not on every object.** `Cart`, `Order`, `CheckoutTotals` and
`ShippingQuote` all carry a `currency` field. `Product`, `ProductVariant`, `CartItem`
and `OrderItem` do **not** — the model default is EGP and the serializers omit the
currency column. Read currency from the enclosing cart/order, and default to `EGP`.

Never do arithmetic on these in JS:

```ts
// Wrong — floats, and it duplicates server logic
const total = Number(subtotal) + Number(shipping) - Number(discount);
```

The server computes every total. Your job is to display `grand_total`. If you need
arithmetic for something the server doesn't provide (a "you saved X" badge from
`compare_at_price` − `price`, say), use a decimal library or integer piastres — never
`Number` + `toFixed`.

### Formatting

```ts
const fmtEGP = new Intl.NumberFormat("ar-EG", {
  style: "currency",
  currency: "EGP",
  minimumFractionDigits: 2,
});

fmtEGP.format(Number(order.grand_total)); // ٥٤٢٫٤٨ ج.م.‏
```

`Number()` at the display boundary only is fine — you're rendering, not calculating.

One decision to make deliberately: `ar-EG` renders Arabic-Indic digits (٥٤٢). Some
Egyptian users expect Western digits even in Arabic UI, and price comparison is harder
in mixed scripts. If you want Arabic text with Western digits, use the numbering-system
extension:

```ts
new Intl.NumberFormat("ar-EG-u-nu-latn", { style: "currency", currency: "EGP" });
// ‏542.48 ج.م.‏
```

Pick one and apply it everywhere — mixing digit systems between the product card and the
checkout total looks broken.

## Dates and times

All datetimes are ISO-8601 with an offset (`DATETIME_FORMAT = "iso-8601"`, `USE_TZ`):

```
"2026-09-20T14:32:05.123456+03:00"
```

Server time is **Africa/Cairo (UTC+02:00, UTC+03:00 in DST)**. Egypt reinstated DST in
2023, so the offset genuinely changes during the year — never hardcode `+02:00`, and
never do date arithmetic on the string.

```ts
const fmtDate = new Intl.DateTimeFormat("ar-EG", { dateStyle: "long", timeStyle: "short" });
fmtDate.format(new Date(order.created_at));
```

Some fields are plain dates, not datetimes: `subscription.start_date`, `next_order_date`,
`ShipmentTracking.estimated_delivery`, `batch.expiry_date`. `new Date("2026-09-01")`
parses as **UTC midnight**, which renders as the previous day in some western timezones —
parse date-only values as local, or format them as strings without going through `Date`.

Business logic keyed to dates — the 14-day return window, for instance — should compare
against server-provided timestamps (`delivered_at`), not the browser's clock, which the
user can change.

`order_number` embeds the Cairo-local date: `ORD-20260920-00001`. Don't parse it for a
date; use `created_at`.

## Phone numbers

`PhoneNumberField` on both `User.phone` and `Address.phone`. Send and expect **E.164**:

```
+201001234567
```

Not `01001234567`, not `0100 123 4567`. Normalize before submitting — Egyptian users
will type the local `01xxxxxxxxx` form:

```ts
export function toE164Egypt(input: string): string {
  const digits = input.replace(/\D/g, "");
  if (digits.startsWith("20")) return `+${digits}`;
  if (digits.startsWith("0")) return `+20${digits.slice(1)}`;
  return `+20${digits}`;
}
```

A bad number comes back as a `VALIDATION_ERROR` with the field name in `errors.fields`.
`libphonenumber-js` is worth the bundle cost if you want to validate before submitting.

## RTL layout

The API is layout-agnostic; RTL is entirely yours. The parts that interact with API data:

**Direction follows the content language, not the user's locale.** Set `dir` on the
document root when the language switches, and use logical CSS properties
(`margin-inline-start`, `padding-inline-end`, `inset-inline-start`) so a single
stylesheet serves both directions.

```tsx
<html lang={lang} dir={lang === "ar" ? "rtl" : "ltr"}>
```

**Mixed-direction strings need isolation.** Product names, SKUs, order numbers and
tracking numbers are Latin and will scramble when interpolated into Arabic text — the
classic "طلب رقم ORD-20260920-00001" rendering with the number in the wrong place. Wrap
them:

```tsx
<span dir="ltr" style={{ unicodeBidi: "isolate" }}>{order.order_number}</span>
```

Or use `&#8296;`/`&#8297;` (FSI/PDI) in plain strings. This applies to `order_number`,
`sku`, `barcode`, `tracking_number`, phone numbers, email addresses and prices with a
Latin currency code.

**Prices in RTL.** `Intl.NumberFormat` places the currency symbol correctly for the
locale; don't concatenate `price + " EGP"` by hand — in RTL that lands on the wrong side.

**Images and icons.** Directional icons (arrows, chevrons, "next page") must flip;
logos and product photos must not. `transform: scaleX(-1)` under `[dir="rtl"]`, applied
per-icon rather than globally.

## Search with Arabic input

`GET /search/?q=` runs Postgres full-text search weighted across `name_en`, `name_ar`,
SKU, barcode, brand and category names, and description. Arabic queries do reach the
Arabic name column, so the basics work.

What to expect: Postgres's default text search configuration doesn't stem Arabic or
normalize the alef variants (أ / إ / ا) or taa marbuta (ة / ه), so "عسل" and "العسل" may
rank differently and a misspelled hamza may miss. Normalize the user's input before
sending it if search quality matters:

```ts
const normalizeArabic = (s: string) =>
  s.replace(/[ً-ْ]/g, "")  // strip diacritics
   .replace(/[أإآ]/g, "ا")
   .replace(/ى/g, "ي")
   .replace(/ة/g, "ه")
   .trim();
```

That helps the query side only — the indexed side is unnormalized, so it's a partial
fix. Proper Arabic search is a backend change (a custom text search configuration, or a
dedicated search engine). Raise it if search is a core part of the product.

`q` is required; an empty `q` is `400 VALIDATION_ERROR`, so don't fire the request until
the input has content.

## A checklist before launch

- [ ] Language switcher sets `<html lang dir>` and persists to `profile.language`.
- [ ] Every user-visible string from the API is either bilingual data (`*_ar`) or mapped
      client-side from a code. No raw server `message` in a primary position.
- [ ] Cart and order pages don't fall back to English product names — or the team has
      accepted that they do, in writing.
- [ ] One digit system, everywhere.
- [ ] Order numbers, SKUs and tracking numbers are bidi-isolated.
- [ ] Phone input normalizes to E.164 before submitting.
- [ ] Date-only fields aren't off by one.
- [ ] Arabic search tested with and without the definite article.
